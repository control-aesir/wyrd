# v0.2.0-alpha release readiness review

Reviewed commit: `4877b1e319692d8856a07a876fabe8c6f3c8f174` (tag ancestry: `v0.1.0-alpha.1`; 578 commits after that tag). Source was exported to `/tmp/wyrd-review-4877b1` so the audit targeted the requested commit while preserving the checkout. ## 1. Verdict

**DO NOT SHIP.** At least one explicitly excluded behavior (production recovery grafting) is exposed in the production sync API. The v0.2 relay interoperability and disconnected history catch-up requirements are not established by the checked-in evidence: the live topology harness uses one relay implementation, and the real-iroh tests are relay-disabled loopback. The required build/test/clippy validation could not get past the sandbox’s Nix clang temporary-file failure, and the full relay/FUSE topology was not run here. Those validations remain UNVERIFIED, not PASS.

## 2. Blockers (ordered)

### B1 — v0.2 exposes recovery grafting despite the explicit exclusion

`ROADMAP.md:193-195` says “Explicitly do not ship: recovery grafting”; `ROADMAP.md:204-206` says stranded local content has no sanctioned path until v0.3. Yet `Engine::author_recovery_snapshot` is a public production method in `crates/wyrd-sync/src/runtime/engine/mod.rs:1185-1205`, calling the authoring implementation. Public API contracts exercise production authoring and materialization at `crates/wyrd-contracts/src/sync_contracts.rs:2288-2370` (`recovery_rebuilds_explicit_historical_content_and_mounts`) and `:2386-2550` (`recovery_resurrects_bytes_from_a_voided_branch_and_mounts`). The production feature is therefore landed, not merely a test fixture.

**Minimal fix:** remove/defer the public authoring entry point from the v0.2 build and keep recovery-graft end-to-end contracts out of the v0.2 shipped surface; alternatively move the milestone boundary and explicitly revise the v0.2 exclusion/limitation before release. Do not silently call this crash recovery: it republishes historical content.

### B2 — relay interoperability is claimed by the milestone but has no cross-implementation evidence

The ship list explicitly includes “multi-relay mailbox operation, relay interoperability” (`ROADMAP.md:185-186`). `tests/alpha-microvm.sh` configures one relay URL (`:35-40` and `:40` default) and the host topology runs that relay service; it does not test a second relay implementation. Mailbox tests use `MiniRelay` (`crates/wyrd-core/src/mailbox/tests_harness.rs:1-2`) or in-memory mailbox/relay fakes (`docs/sync-and-peers.md:46-48`). No checked-in test or recorded command proves interoperability with an independently implemented relay. Repeatable `--relay` parsing (`crates/wyrd-cli/src/main.rs:65-75`) and relay supervision code (`crates/wyrd-core/src/mailbox/mod.rs:1233-1495`) establish implementation intent, not interoperability.

**Minimal fix:** add and run a two-relay cross-implementation contract that demonstrates addressed event publication, subscription/replay, duplicate handling, relay loss/recovery, and continued intake; otherwise remove interoperability from the v0.2 ship claim and keep release blocked on it.

The ignored `external_relay_gift_wrap_round_trip_over_tls` and `external_relay_restart_replay_converges` tests in `crates/wyrd-core/src/mailbox/tests_interop.rs:20-145` are useful real-public-relay evidence when explicitly run, but each targets one relay URL (default `nos.lol`) and is opt-in. They do not prove cross-implementation interoperability or multi-relay behavior. No successful run output was available.

### B3 — disconnected history catch-up is not demonstrated over real relay infrastructure

The DoD separates “history catch-up after disconnection” from state convergence (`ROADMAP.md:197-202`). The contracts do test ordered/reversed/duplicated catch-up (`crates/wyrd-contracts/src/join_contracts.rs:225-326`) and runtime state convergence (`crates/wyrd-sync/src/runtime/engine/tests_properties.rs:84-145`), but these use in-memory relay/bulk fixtures. The real transport serving tests explicitly construct relay-disabled iroh endpoints (`crates/wyrd-contracts/src/serving_contracts.rs:1-7, 106-116`); they prove content acquisition and route change over loopback, not relayed catch-up. The microVM shell has real relay convergence/restart/partition legs (`tests/alpha-microvm.sh:193-325`), but the inspected legs do not independently prove that a peer reconnecting after missing a sequence of snapshots obtains and verifies the complete history closure before becoming converged. Thus state convergence has stronger live evidence than history acquisition.

**Minimal fix:** add a real-relay test that disconnects a previously admitted peer, authors multiple ordinary snapshots including content/history dependencies, reconnects it, and independently asserts (1) history closure/body/manifest acquisition and (2) live-head/state convergence, with restart and invalid/missing-object controls. Run it on the Linux KVM gate and retain logs.

### B4 — automatic peer repair is listed for v0.2 but is not wired at runtime

The v0.2 Ship list includes “peer repair” (`ROADMAP.md:185-186`). The README explicitly says “automatic peer repair is not yet wired at runtime” (`README.md:45-46`), while describing bulk fetch and a serving router as existing. The current serving contract proves a peer can fetch announced representations over iroh (`crates/wyrd-contracts/src/serving_contracts.rs:16-100`); it does not prove corruption detection selects another provider and repairs the object. `docs/sync-and-peers.md:230-244` overstates the behavior by saying corrupt objects trigger scrub/repair before surfacing.

**Minimal fix:** wire and test alternate-peer repair with post-fetch content-hash verification, or explicitly defer peer repair from v0.2 and correct the sync contract/README so no user expects it.

### B5 — baseline correctness gate is unverified in this environment

`cargo build --workspace`, `cargo test --workspace`, and `cargo clippy --workspace --all-targets` all stop while compiling `ring`; the Nix-wrapped clang warns about `--target arm64-apple-macosx` and fails `unable to make temporary file: Operation not permitted` while trying to create an iOS assembly object. No project compile/test result was reached. `devenv shell -- cargo build --workspace` also fails resolving its pinned input because Nix cannot open `/Users/thomas/.cache/nix/fetcher-locks/...lock` (`Operation not permitted`). This is not evidence of a product-code failure, but the release gate is not green.

**Minimal fix:** run the exact workspace build/test/clippy commands in the repository’s supported devenv on a host with writable Nix/Cargo temp/cache paths, then run the platform FUSE suite and the KVM relay suite; attach exact output and failures.

### B6 — release distribution is enabled and documented despite the v0.2 exclusion

`ROADMAP.md:193-195` explicitly excludes “release distribution”. The README says prebuilt archives ship with each ngit release and documents `nix build .#wyrd-dist` (`README.md:213-216`). This is backed by an actual release manifest (`.ngit/release.yaml:1-39,54-67`), a distribution workflow (`.ngit/act/workflows/dist.yml:4-17,63-86`), and release build tooling (`.ngit/scripts/build.sh:231-234`). This is more than an aspirational sentence: the repository has the distribution and publication path prepared, contrary to the milestone boundary. No remote v0.2 publication was attempted in this review.

**Minimal fix:** keep the v0.2 artifacts unpublished and remove/disable the release-distribution path for this milestone, or make a recorded scope decision that explicitly supersedes the roadmap exclusion before publishing.

## 3. Non-blocking issues

- **Milestone/docs drift:** `ROADMAP.md:110-112` still calls the serving router/real-iroh loopback remaining, while `docs/architecture.md:189-199` says the serving router and restart route rewiring landed (contract 13). Conversely, README still calls relay-pool supervision and multi-relay supervision open (`README.md:95-97, 256-262`), while architecture describes a live supervised mailbox and multi-relay recovery (`docs/architecture.md:176-199`). Update the roadmap/README to distinguish shipped code, verified scope, and remaining evidence.
- **Bulk backpressure wording is stale/underspecified:** roadmap Phase 1 still lists bulk backpressure under live network conditions as remaining (`ROADMAP.md:110-112`), while `docs/resource-limits.md:104-116` and `crates/wyrd-contracts/src/sync_contracts.rs:1588` describe bounds/fail-closed behavior. The contract suite is not a live network saturation test; state that difference explicitly.
- **NIP-46 client wiring remains absent.** The concrete `SignerSession`/NIP-46 client negotiation is deferred (`docs/sync-and-peers.md:49-55`, `docs/architecture.md:198-199`). The normative trust doc treats remote signing as optional/scoped/default-deny (`docs/trust.md:789-811`), so this is not independently a v0.2 blocker if local signing is the supported mode, but the roadmap should say so.
- **Automatic peer repair claims conflict:** README says automatic peer repair is “not yet wired at runtime” (`README.md:95-97`); `docs/sync-and-peers.md` says corrupt objects trigger scrub/repair before surfacing (`:230-244`). Treat automatic repair as unavailable until a runtime test proves detection, alternate-peer acquisition, and hash verification; correct the stronger doc claim.
- **Ignored tests:** `crates/wyrd-cli/src/tests_mount.rs:227-237` ignores `live_mount_serves_read_write_until_shutdown` unless explicitly run with kernel FUSE/network. `crates/wyrd-contracts/src/upgrade_contracts.rs` contains deliberately ignored future upgrade tests; `crates/wyrd-contracts/src/lib.rs:182-185` names two, and source has further `#[ignore]` cases at `upgrade_contracts.rs:169,244,259,353`. These do not all target v0.2, but must not be counted as passing coverage.
- **History limitation incomplete for ordinary peers:** roadmap documents stranded *local* content and cooperative local writers (`ROADMAP.md:204-207`), but does not say what happens when a remote’s announcement/history is retained while its serving endpoint and all alternate holders are gone. The product behavior appears to be bounded `EIO` on missing content (`docs/fetch-on-open.md:121-160` and `README.md:251-254`); document the no-provider case and whether a partial history remains visible.
- **Terminology:** roadmap’s recovery taxonomy is careful (`ROADMAP.md:75-82`), but the shipped public `author_recovery_snapshot` naming and v0.2 excluded grafting feature make broad “recovery” wording ambiguous. Use “crash recovery”, “content recovery”, and “root recovery” every time, and do not imply v0.2 supplies content/root recovery.
